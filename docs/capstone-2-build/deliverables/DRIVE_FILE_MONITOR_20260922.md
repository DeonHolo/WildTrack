# Deadline-aware Drive PDF monitoring, September 22, 2026

**State: implementation and simulated-provider tests completed locally; no real-user monitoring verified in this change.** An admin can enable or disable monitoring separately for each active academic workspace in Workspace setup; no environment flag or workspace UUID entry is needed. A configuration dialog chooses the specific deliverables to monitor, including an intentional empty selection. Migration V30 preserves the existing default-all selection only until an Admin first saves explicit deliverable choices; new deliverables then default unselected. The worker operates only on eligible saved, unarchived PDF artifact links for selected deliverables within enabled workspaces. No permanent PDFs are stored. Monitoring is engineering evidence and does not count toward student Goal 3 scores.

## Operation

The opt-in worker recalculates eligible unique Drive file IDs from saved form responses of **selected deliverables** in each enabled active workspace once per minute. It derives each file's monitoring priority from its associated selected-deliverable deadlines in Asia/Manila. An initial observation uses earlier actual Document Check metadata when available. Without a prior observed checksum, a first metadata read does not reconstruct what was present at submission time.

Normally a file receives one metadata-only request per hour. From 24 hours before until 48 hours after the deadline, the interval is five minutes. The default cap of 20 unique metadata checks per minute spreads an initial set of 60 shared PDFs over approximately three cycles, subject to provider delays. Moving a deadline nearer recalculates the priority on the next minute tick. A finalized archived response version stops being monitored; a subsequently saved version remains eligible.

Unchanged checksums require no PDF download or parse. A verified new checksum, even a small modification, triggers one shared file download and PDF parse for all associated responses. Each individual response retains its own field-scoped Document Check report, original saved timestamps and distinct template/academic context. Previous reports are preserved. The manual Recheck all documents and Check all unchecked actions also batch by canonical file ID before progressive chunking, avoiding repeated downloads when five team members submit the same shared PDF.

Monitoring events distinguish CONTENT_CHANGED, ACCESS_UNAVAILABLE, DOWNLOAD_UNAVAILABLE, FILE_TYPE_CHANGED, CHANGE_AWAITING_CHECK and informational METADATA_CHANGED or ACCESS_RESTORED. Today’s Work presents one prominent unresolved significant event per file with affected-submissions count and names/identifiers of up to two linked students (plus any further count). When the same Drive file is also submitted under an unselected deliverable, event recipients are filtered to selected deliverables, so staff cannot mistake excluded submissions for monitored ones. Personal Open/Dismissed tabs retain staff dismissals without deleting history; selected-category Dismiss all/Restore all operate across all category items rather than only searched or paginated rows. A genuinely newer significant event can surface after an older one was dismissed. No academic acceptance or grade changes automatically.

An unexpected provider metadata file ID is rejected rather than being recorded under a different submitted link. When the provider has no comparable MD5 checksum but reports a newer modification time, WildTrack re-downloads/rechecks the current PDF once and records an explicitly **unverified** change observation. That metadata timestamp alone is not represented as proof of different PDF bytes. A temporary provider failure preserves the last known accessibility observation instead of manufacturing an access-restoration alert. Staff event visibility is mapped only through actual active submitted PDF fields in the staff member's authorized teams, never through an arbitrary free-text field containing a Drive URL. An acknowledged newer significant event does not conceal an earlier undismissed significant event for the same file.

## Controlled enablement

Open **Workspace setup** as an Admin and select the active workspace. The panel has a compact **?** tooltip explaining that each deliverable's Asia/Manila due date determines ~hourly checks normally and ~five-minute checks from 24 hours before through 48 hours after that deadline, subject to a 60-second worker tick, the per-workspace 20-file-per-cycle cap, access and Drive quota. Click **Configure deliverables** to select one, several, all or none of the eligible PDF deliverables; Save records the exact selection in the database (none means no automatic scans even while enabled). Click **Enable monitoring** or **Disable monitoring** separately; selection survives disabling. Newly created deliverables do not turn on silently after an explicit selection has been saved. An archived workspace is never scanned. Activation is blocked when the existing Drive gateway is unconfigured. Optional WILDTRACK_FILE_MONITOR_MAX_FILES_PER_CYCLE and WILDTRACK_FILE_MONITOR_TICK_MS remain operator pacing settings, never prerequisites to the UI switch. No copied UUID, monitoring env flag, new OAuth scope or student loading screen is required. Students still must submit Drive files WildTrack can read.

## Evidence boundaries

Local automated tests used 300 fictional response records sharing 60 file IDs, five synthetic students sharing one generated PDF with mocked provider metadata/downloads, and staff-authorization checks. They do NOT verify deployed browser behavior, live Google Drive file access, or real student submissions. A five-minute interval is a scheduling target, not a guarantee under provider outages or backlog. Same-link replace-and-restore between observations can escape detection; checksum changes prove different bytes, not intent, materiality or exact contents at the deadline. Metadata-only modifications do not prove a PDF content edit. Native Google Docs/Sheets/Forms have different metadata and are not treated as uploaded binary PDF files. The monitor preserves small metadata and reports only, not immutable PDF snapshots. An in-flight file check may finish if an admin disables monitoring at the same time; the next file will not be checked.
